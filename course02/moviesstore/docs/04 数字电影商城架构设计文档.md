## 二、系统目标与边界

### 2.1 系统目标

系统以“数字电影内容交付”为核心，构建完整闭环：

- 多登录体系：用户名/邮箱/手机号 + 密码 + OTP；第三方登录（微信/QQ）可扩展
- 金币内循环：充值入账 → 钱包余额 → 消费扣减 → 授权发放
- 权限判定清晰：购买权限优先，会员仅授予播放，不授予下载
- 下载风控：设备绑定 + token 过期 + 每日配额限制
- 工程化：业务逻辑集中在 Service 层，支持 TDD 与可演进扩展



### 2.2 系统边界

系统不包含或弱化以下能力（可后续规划）：

- 复杂运营体系（券、活动、返利）
- 推荐算法与大数据分析链路
- 实体物流与售后
- 全量内容爬取与外部数据同步（评分可手动录入或定时同步）



## 三、总体架构

### 3.1 架构分层

后端采用四层结构：

**接口层（API / DRF View、ViewSet）**

- 负责：鉴权、参数校验、调用 Service、统一响应封装
- 不允许：业务事务、复杂判断、跨表写入

**业务服务层（Service）**

- 负责：核心业务编排、事务边界、幂等、风控、权限判定、跨域调用
- 项目“灵魂”所在，所有复杂逻辑必须集中在此层

**领域模型层（Domain / ORM）**

- ORM Model：字段、索引、约束、最小模型方法
- 不允许：大段业务流程写在 Model method 中

**基础设施层（Infrastructure）**

- MySQL（持久化）
- Redis（缓存、限流、分布式锁/幂等辅助）
- 对象存储 + CDN（视频与图片）
- 消息队列（可选，后续异步处理）



### 3.2 前后端关系

- React 负责页面渲染与交互
- Django/DRF 提供 REST API
- JWT 鉴权，前端存储 access token，必要时配 refresh token（可选）



## 四、代码工程结构（目录规范）

### 4.1 项目结构

建议统一采用 `apps` 目录承载所有业务模块，Django 核心配置目录命名为 `config`：

```
project_root/
├── config/                 # Django 项目配置（settings/urls/asgi/wsgi）
├── apps/
│   ├── auth/               # 认证域：identity、otp、oauth
│   ├── accounts/           # 用户域：users、device
│   ├── content/            # 内容域：movie、detail、asset、people
│   ├── wallet/             # 资金域：wallet、coin_transaction
│   ├── payment/            # 支付域：recharge_order、auto_debit_agreement
│   ├── orders/             # 交易域：purchase_order、item、license
│   ├── membership/         # 会员域：membership、renewal
│   └── download/           # 下载域：download_token、quota
├── scripts/                # 脚本：init_data 等（必须在根目录执行）
├── requirements.txt
├── .env
└── manage.py
```



### 4.2 模块依赖约束（必须遵守）

依赖方向只允许“向内”和“向基础域”，避免循环依赖：

- content 不依赖任何交易/资金模块
- auth/accounts 为基础域，可被其他模块依赖
- wallet/payment 为资金域，可被 orders/membership/download 依赖
- orders 可依赖 content（读取电影信息）、wallet（扣币）、accounts（用户）
- membership 可依赖 wallet/payment（续费链路）、accounts
- download 可依赖 orders（license 授权校验）、accounts（设备校验）

禁止：

- content 依赖 orders
- wallet 依赖 orders
- 循环依赖（A → B → A）



## 五、关键业务域设计

### 5.1 认证域（Auth）

目标：支持多身份、多因子、第三方登录的扩展，不污染业务域。

核心表（概念）：

- users：用户主体（含 password_hash）
- user_identity：用户名/邮箱/手机号登录标识
- auth_otp：短信/邮件 OTP（登录、MFA、注册、重置）
- oauth_account：第三方账号绑定（WECHAT/QQ 等）

认证流程统一为：

1. Identifier 定位 user（identity 或 oauth）
2. 校验 password（可选）
3. 校验 OTP（可选，用于 MFA 或无密码登录）
4. 设备绑定写入（user_login_device）
5. 颁发 JWT



### 5.2 用户域（Accounts）

- users：用户主体状态、密码哈希、最后登录时间
- user_login_device：登录设备绑定与限制（最大设备数）



### 5.3 内容域（Content）

采用“基础 + 详情 + 资源 + 演职人员”模型：

- movie：商城视角（定价、access_type、上架）
- movie_detail：内容视角（评分、片长、产地、简介等）
- movie_asset：封面、海报、剧照、视频、预告片
- people / movie_people：导演、编剧、演员等结构化关联



### 5.4 资金域（Wallet）

金币内循环模型：

- wallet：余额快照
- coin_transaction：账本流水（所有变更必须记录）



### 5.5 支付域（Payment）

- recharge_order：真实支付充值订单（回调幂等）
- auto_debit_agreement：代扣协议（会员自动续费）



### 5.6 交易域（Orders）

- purchase_order：消费订单主表
- purchase_order_item：订单项（电影维度）
- purchase_license：购买授权（user_id + movie_id 唯一）

关键原则：

- 播放/下载权限不依赖订单状态，最终以 license 为准
- order_item 为退款、下载凭证、授权关联的最小粒度



### 5.7 会员域（Membership）

- membership：会员状态机（ACTIVE / GRACE / EXPIRED）
- membership_renewal：续费记录（关联充值订单）

关键原则：

- 会员仅授予播放 access_type=BUY_OR_VIP 的权限
- 会员永不授予下载权限



### 5.8 下载与风控域（Download）

- download_token：一次性下载凭证（过期、绑定 device）
- download_daily_quota：按 user+movie+date 限制每日生成次数

关键原则：

- token 过期（例如 5 分钟）
- 必须绑定设备（device 必须来自登录设备）
- 必须校验购买授权（license）



## 六、核心业务流程（时序与事务边界）

### 6.1 充值入账（支付回调幂等）

目标：保证“多次回调不重复入账”。

流程：

1. 创建 recharge_order（CREATED）
2. 第三方支付成功回调到后端
3. 校验签名与 out_trade_no
4. 幂等检查：若 recharge_order 已 SUCCESS，直接返回成功
5. 开启事务：
    1. 锁定 wallet 行（SELECT ... FOR UPDATE）
    2. 增加 wallet.balance
    3. 插入 coin_transaction（RECHARGE）
    4. 更新 recharge_order.status = SUCCESS
6. 事务提交，返回余额

幂等点：

- recharge_order.out_trade_no 唯一
- status 状态机约束



### 6.2 购买电影（扣币 + 发放授权）

目标：扣币与授权发放必须原子化。

流程：

1. 校验 movie.status = ONLINE
2. 校验 access_type：若 FREE 则不允许购买或返回已免费
3. 创建 purchase_order（CREATED）
4. 开启事务：
    1. 锁 wallet 行
    2. 校验 balance >= price_coin
    3. 扣减 wallet.balance
    4. 写 coin_transaction（PURCHASE）
    5. 写 purchase_order_item（movie_id, price_coin）
    6. 写 purchase_license（user_id, movie_id, order_item_id）
    7. 更新 purchase_order.status = COMPLETED
5. 事务提交
6. 返回订单与授权结果

幂等点：

- purchase_license(user_id, movie_id) 唯一键防止重复授权
- 业务层可在下单前检查是否已授权



### 6.3 会员开通/续费（真实支付 → 充值 → 扣币 → 续期）

目标：会员续期必须走金币体系。

流程（自动续费与手动续费统一）：

1. 代扣或用户支付创建 recharge_order
2. 支付成功回调触发“充值入账”（同 6.1）
3. 开启事务：
    1. 锁 wallet
    2. 校验余额
    3. 扣减金币
    4. coin_transaction（RENEW）
    5. 更新 membership：end_at 顺延、status 更新
    6. 写 membership_renewal（关联 recharge_order）
4. 返回续期结果

幂等点：

- membership_renewal(recharge_order_id) 可设唯一（建议）
- 续期操作对同一 recharge_order 只能执行一次



### 6.4 下载令牌生成（风控核心）

目标：生成一次可过期、可审计、可限制的下载凭证。

流程：

1. 校验设备已绑定：user_login_device 存在且有效
2. 校验购买授权：purchase_license 存在
3. 开启事务：
    1. 锁定 download_daily_quota（按 user_id + movie_id + date）
    2. 若不存在则创建 count=0
    3. 判断 count < daily_limit，否则拒绝
    4. count += 1
    5. 写 download_token（expires_at = now + 5min）
4. 返回 download_token（或进一步签名下载 URL）

幂等点：

- download_daily_quota(user_id, movie_id, date) 唯一键防并发
- token 本身无需幂等（每次生成消耗配额）



## 七、权限与风控策略（必须固化）

### 7.1 播放权限判定（Policy）

判定顺序：

1. 若存在 purchase_license（user_id, movie_id）→ 允许播放
2. 若 movie.access_type = BUY_OR_VIP 且 membership 为 ACTIVE 或 GRACE → 允许播放
3. 若 movie.access_type = FREE → 允许播放
4. 否则拒绝

原则：

- 购买权限优先于会员权限
- GRACE 宽限期保留播放权限



### 7.2 下载权限判定（Policy）

1. 必须存在 purchase_license
2. 必须设备已绑定（user_login_device）
3. 必须未超过每日配额
4. 生成 download_token 才允许下载

原则：

- 会员永不授予下载权限



### 7.3 设备限制策略

- 最大登录设备数（例如 2）
- 超过限制：拒绝登录或提示解绑设备
- 下载设备必须来自登录设备集合



### 7.4 OTP 安全策略

- code_hash 存储，不存明文
- attempts 限制（如 5 次）
- expires_at 过期即失效
- consumed_at 防止重复使用
- 同 receiver 在短时间内限流（建议 Redis）



## 八、缓存、限流与异步（基础设施策略）

### 8.1 Redis 使用建议

- 热门电影列表缓存（首页/榜单）
- OTP 发送频率限流（按手机号/邮箱）
- 登录失败次数限制（按 identifier + ip）
- 下载接口限流（按 user_id + ip）
- 可选：幂等 key（如支付回调处理锁）



### 8.2 异步任务（可选）

可后续引入 Celery/RQ：

- 支付回调后异步通知
- 影片资源转码与截图
- 定时同步评分数据（IMDb/豆瓣等）
- 会员到期状态扫描（或通过查询实时判断）



## 九、API 设计规范

### 9.1 接口分组（建议最小集合）

认证：

- POST /api/auth/login
- POST /api/auth/login-otp
- POST /api/auth/mfa/verify
- POST /api/auth/oauth/wechat
- POST /api/auth/oauth/qq

内容：

- GET /api/movies
- GET /api/movies/{id}

钱包：

- GET /api/wallet
- POST /api/wallet/recharge

交易：

- POST /api/orders/purchase
- GET /api/orders
- GET /api/orders/{id}

会员：

- GET /api/membership
- POST /api/membership/renew

下载：

- POST /api/download/token



### 9.2 返回结构统一

统一返回结构由 View/ViewSet 层 Mixin 封装（不依赖 Renderer）：

- code：业务码（0 成功，非 0 失败）
- message：提示信息
- data：返回数据

错误码建议按域划分：

- 1xxx：认证
- 2xxx：内容
- 3xxx：钱包
- 4xxx：订单
- 5xxx：会员
- 6xxx：下载风控



## 十、数据一致性与幂等策略汇总

### 10.1 事务边界（必须事务）

- 充值入账：wallet + coin_transaction + recharge_order
- 扣币购买：wallet + coin_transaction + order + item + license
- 会员续期：wallet + coin_transaction + membership + renewal
- 下载配额：quota + token



### 10.2 唯一键保证幂等（建议清单）

- recharge_order.out_trade_no UNIQUE
- user_identity(identity_type, identifier) UNIQUE
- oauth_account(provider, open_id/union_id/subject) UNIQUE（按接入字段）
- purchase_license(user_id, movie_id) UNIQUE
- purchase_license.order_item_id UNIQUE
- download_daily_quota(user_id, movie_id, date) UNIQUE
- membership_renewal(recharge_order_id) UNIQUE（建议）



## 十一、测试策略（TDD 建议）
